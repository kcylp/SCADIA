## 3. 本会话的两个关键发现（**必须知道，否则会误判**）

### 发现 A：内存报警检测**完全无法触发**（已修复）

- 报警引擎 `runtime/alarms/index.js` 读 `tag.ts` 当采集时间，传给 `Alarm.check(time, dt, ...)`，`dt` 用作 `ontime`。
- **代码库中从未有任何地方写入 `ts`**；所有驱动写的是 `tag.timestamp`（20 处）。
- 后果：`ontime = undefined` → 下一轮 `ontime + checkdelay*1000 <= time` 恒为 `false` → **一条内存报警也产生不了**。
- 证据：全库检索 `.ts =` → 0 命中；运行时探针 → `stored.ts = undefined` 而 `stored.timestamp` 有值；插桩 → `rc=false ontime=undefined`。
- 修复：改读 `tag.timestamp`，缺失时回退到本次检查时刻 `time`。
- **台账 L-28**。

### 发现 B：测试存在隐式全局 `expect`（已修复）

- 4 个文件写 `global.expect = chai.expect;`；`runtimeUtilsTypes.test.js` **完全没声明却直接用 `expect`**（靠泄漏存活）。
- 后果：测试互相依赖、依赖文件加载顺序。
- 修复：全部改为文件顶部 `const { expect } = require('chai')`；5 个文件**隔离运行全部通过**。
- **台账 L-27**。

## 4. 下一步：CODE-6 的具体做法（已规划，直接执行）

**契约依据**：`10_契约03_DAQ查询语义.md` ｜ 台账 **L-14**。

### 现状（已实测）

- `devices/index.js` 的 `getHistoricalTags(tagIds, fromTs, toTs)` → `daqstorage.js` 的 `getNodesValues()`。
- 无 options 时（`daqstorage.js` 约 119-124 行）返回 `{tagId:[{x,y}]}`，并在两端各插一个 `y:null` 端点。
- **查不到节点直接 `resolve([])`** —— 与"数值没跨死区""设备断线""采集停止""归档失败"**完全不可区分**。
- 结果里**没有 quality 字段**（全平台只有 `runtime/index.js` 的 `tagsToSend` 传 quality）。
- 无范围/点数/并发/超时限制，无取消。

### 实施步骤（低风险优先，向后兼容）

1. **先写测试**：`test/storage/daqQueryContract.test.js`（用 SQLite 后端 + 临时目录），覆盖：
   - 区间为 **[from, to)**；
   - **未知 tagId 不再与"空数据"同形**（返回可判定的状态）；
   - 未启用 DAQ 的 tag 返回 `daq-disabled`；
   - 缺失/缺口可被识别；
   - 超范围/超点数被**明确拒绝**而不是静默截断。
2. **新增查询入口而非改旧签名**：新增 `getHistoricalTagsV2(tagIds, fromTs, toTs, options)`（或给 `getHistoricalTags` 增加可选 `options`），返回
   `{ series: {tagId:[{t, v, quality}]}, status: {...}, gaps: [...], resolution, ... }`；
   **原 `getHistoricalTags` 保持原样**，避免破坏 Node-RED 节点、脚本 `$getHistoricalTags`、报表等既有消费者。
3. **限额**：maxRangeMs / maxPoints / concurrency / timeout，超限返回明确错误码。
4. **门禁**：全量 mocha 必须仍 0 failing；并确认 `report.js`、node-red 节点、脚本 `$getHistoricalTags` 不回归。
