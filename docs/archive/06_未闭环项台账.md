#### F.2 内存报警检测缺陷的证据（L-28）

**现象**：`Alarm.check(time, dt, value, displayValue)` 用 `dt` 作为 `ontime` 起点，并在下一轮用
`this.ontime + (checkdelay * 1000) <= time` 判定。`dt` 来自 `_checkAlarms` 的 `tag.ts`。

**证据链**：
1. 全库检索 `.ts =`（赋值）→ **0 处命中**；
2. 全库检索 `tag.ts`（读取）→ 仅 `runtime/alarms/index.js`；
3. 运行时探针：真实 `tagValueCompose` + 驱动存储对象形状为
   `{id, type, rawValue, value, changed, tagref, timestamp}` → **`ts === undefined`、`timestamp` 有值**；
4. 插桩确认：`rc=false statusAfter= ontime=undefined ts=undefined`。

**影响**：内存中的实时报警**一条也不会产生**（`ontime` 永远不是有效时间戳）。报警历史读写路径本身正常，因此该缺陷可长期潜伏。

**修复**：`runtime/alarms/index.js` 改读 `tag.timestamp`，缺失时回退到本次检查时刻 `time`，使报警能够正常激活而不是恒为 `false`。

**验证**：`test/devices/deadbandAlarm.test.js` 中「99 → 101 / 死区 10 / 阈值 100」用例
在修复前**失败**（无报警），修复后**通过**且报警记录值 = 101。

#### 4.6.1 一条必须记录在案的**错判更正（A-02）**

本窗口早先报告：「UI 选 InfluxDB 1.8 → 静默落进 SQLite」。**该结论是错的。**

* 实测的只是「字符串 `'influxDB 1.8'` 会落进 SQLite」；
* 但**没有验证界面到底发什么**。查证后：模板是 `[value]="type.key"`，而 `EnumToArrayPipe` 的 `key` 取 `Object.keys(enum)` —— 即**成员名**。
  界面实际发的是 `influxDB18`，服务端一直认识它，**活路径从未失效**；
* 真实残留是一个**潜在陷阱**：`DaqStore.type` 声明为枚举值，而 UI 存的是成员名；五个成员里只有 `influxDB18` 两者不同，一旦有人改用枚举值、或标签被改动，就会静默错路由。

处置：服务端提供**单一归一化入口**，两种写法都接受、改写并记日志，未知取值拒绝；
守卫也从「两端枚举看起来一样」改成**「两端能发出的每一种写法都必须解析得到」** —— 后者才是活路径的保证。
