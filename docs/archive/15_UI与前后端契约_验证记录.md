## 7. 第三轮：加载卡住的**真正入口**已定位（2026-09-29）

前一轮我把卡住归因于“画面加载完成前的前置请求”，**这个猜测是错的**。本轮读代码找到了确切入口，并且**顺带发现并修复了一个真实的前端缺陷**。

### 7.1 加载遮罩的确切条件

`home.component.html` 第 1 行：`<div *ngIf="isLoading" …>`，遮罩完全由 `isLoading` 决定。
而 `isLoading = false` **只在 `loadHmi()` 执行到最后才会被设置**。

`loadHmi()` 不是自己启动的，它由事件驱动：

```
ngOnInit()  ->  projectService.onLoadHmi.subscribe(() => this.loadHmi())
onLoadHmi   <-  notifyToLoadHmi()  <-  onRefreshProject()/load() 拿到工程后调用
```

**只要这条链路没走通，遮罩就永久停在屏幕上。**

### 7.2 顺带发现并修复的真实缺陷

`loadHmi()` 原先这样排：

```
viewToShow = await this.projectService.ensureViewLoaded(viewToShow.id);   // 可能 reject
... 一堆设置 ...
this.isLoading = false;                                                   // 只有成功才走到
```

**只要取视图失败（网络抖动、工程被改坏、权限变化），用户看到的就是永不消失的进度条加空白屏幕**，且没有任何提示。这在现场是“系统死了”级别的观感。

**修复**（`client/src/app/home/home.component.ts`）：

| 改动 | 作用 |
|---|---|
| 拆出 `loadHmiInner()`，`loadHmi()` 用 `try/finally` 包裹 | **`isLoading` 无论成败都一定被清除** |
| 视图取数失败 -> `toastr` 提示 + 继续 | 用户知道哪个画面没加载出来，而不是面对白屏 |
| `this.hmi.layout.loginonstart` 改为可选链 | 无 layout 的工程不再可能抛错 |

**验证**：重新 `ng build` **0 error**；并在服务端实际产出的 `main.js`（5.14 MB）中确认包含 `loadHmiInner`、`loadHmi failed`、`could not be loaded`。

### 7.3 为什么 headless 下仍看到遮罩

在真实视图已注入、背景图可达（`GET /api/project/view/... -> 200`、`/api/project` 返回 99 KB）的前提下再测：
**headless Chrome 浏览器侧完全没有发出任何请求** —— 服务端日志里只有我注入数据时的请求，没有任何来自浏览器的 /api/project。
即整条链路根本没启动，属于 headless/虚拟时间下的加载行为问题，**不是应用逻辑缺陷**。

### 7.4 这一轮的净收益

| 项 | 结果 |
|---|---|
| 遮罩条件 | **已定位到行** |
| 新发现的前端缺陷 | **1 个（已修复）**：加载失败永久卡死 |
| 画面成品观感 | 仍未验证（headless 不发起请求） |

**结论不变**：UI 是否达到工业级专业，仍需人工在真实浏览器里确认。但这一轮不是白跑 —— 挖出并修掉了一个会在现场表现为“系统卡死”的缺陷。

## 8. 第四轮：又一个同源缺陷（2026-09-29）

顺着上一轮的线索继续查，发现**同一类问题的第二个实例**。

### 8.1 缺陷

`hmi.layout` 在**真实工程里是可选的** —— 我导出本项目 `general` 表时，里面**只有 `version` 一行，根本没有 layout**。

但 `home.component.ts` 打开页面时有这么一行（无保护）：

```ts
this.scadiaview.hmi.layout = this.hmi.layout;   // hmi.layout 可能不存在
this.scadiaview.loadHmi(this.homeView);
```

**只要 `hmi.layout` 缺失，这里就抛错 → 整个页面打开流程中断 → 又是那个永不消失的加载遮罩。**

上一轮我把登录判断改成了可选链（`this.hmi?.layout?.loginonstart`），**反而让代码更容易走到这一行**，所以这一处必须一起加固 —— 否则等于修了一半。

### 8.2 修复

| 改动 | 作用 |
|---|---|
| `this.scadiaview.hmi.layout = this.hmi?.layout ?? null` | 无 layout 时传 `null` 而不是抛错 |
| 增加 `if (this.scadiaview)` 就绪判断 + 告警 | 视图组件未就绪时给出可追踪日志，不静默 |

**验证**：重新 `ng build` **0 error**。

### 8.3 这两轮合起来说明了什么

两个缺陷是**同一种病**：**页面打开链路上任何一次未处理的异常，都会把用户永久留在加载遮罩里。**

| 轮次 | 缺陷 | 位置 |
|---|---|---|
| 第三轮 | 视图取数失败 → `isLoading` 永不清除 | `loadHmi()` 缺 `finally` |
| 第四轮 | 无 layout → 打开页面抛错 | `openPage()` 无保护读 `hmi.layout` |

**建议**：把“打开链路必须收敛到 `isLoading = false`”作为一条硬约束，新增页面打开分支时一并遵守。这比逐个补 `??` 更可靠。

## 9. 第五轮：headless 阻断原因**已确证为环境问题**（2026-09-29）

前几轮我一直没能解释“浏览器为什么不发请求”。这一轮把它确证了，结论对后续很重要：**不是应用问题，是这个环境里 headless Chrome 连不上本地网络。**

### 9.1 证据链

| 测试 | 结果 |
|---|---|
| PowerShell 请求 `http://127.0.0.1:1899/main.js` | **200**（服务端完全正常） |
| Chrome headless 请求 `data:text/html,<h1>hello</h1>` | **正常输出**（浏览器本身能跑） |
| Chrome headless 请求 `http://127.0.0.1:1899/` | **零输出**，且服务端日志**一行请求都没有** |
| 加 `--no-proxy-server` | 仍然零输出 |
| 改用局域网 IP 访问 | 仍然零输出 |

**关键判据**：服务端日志在 Chrome 运行前后**行数完全一致**（13 到 13），说明 Chrome **一个字节都没发出去**。

### 9.2 已排除的原因

| 猜测 | 结论 |
|---|---|
| 服务端没起来 | **排除**：PowerShell 拿到 200 |
| Chrome 坏了 | **排除**：`data:` URL 正常渲染 |
| 代理拦截 | **排除**：系统代理 `127.0.0.1:7897` 的绕过列表已包含 `127.*` 与 `localhost`；加 `--no-proxy-server` 无效 |
| 应用逻辑不请求 | **排除**：请求根本没到达服务端，谈不上应用逻辑 |

即：这是**沙箱/环境层面**的限制（Chrome 无法访问本机网络），**不是 SCADIA 的缺陷**。

### 9.3 这对 UI 人工走查意味着什么

**我无法在本环境完成「真实浏览器打开页面看观感」。** 这不再是「我没做」，而是「此环境做不到」，并且现在有确证。

需要在**用户本机或任一台能正常上网的机器**上做：

1. `cd source/server` 后 `npm start`（或 `node main.js --port 1899`）；
2. 浏览器打开 `http://127.0.0.1:1881/`；
3. 用 `admin` / `123456` 登录；
4. 逐页看：主页画面、设备页、报警页、视频页、组态编辑器。

### 9.4 本轮净收益

| 项 | 结果 |
|---|---|
| headless 阻断 | **确证为环境问题**（此前只是猜测） |
| 应用可服务性 | 再次确证：静态包、API、DOM 渲染全部正常 |
| 画面成品观感 | **本环境无法验证**（已给出可执行的替代路径） |

## 11. 第七轮：继续静态审计，发现**署名错误**（2026-09-29）

沿着上一轮的静态审计路子，本轮查的是“界面里有没有不该出现的内容”：硬编码文案、调试残留、错误署名。

### 11.1 发现：关于对话框署名了错误的上游团队

两个对话框硬编码了同一句话：

```html
home/userinfo.dialog.html:15    SCADIA powered by <b>frango</b>team
```

## 12. 第八轮：审计“用户可见文案是否绕过 i18n”（2026-09-29）

### 12.2 逐项排除的“疑似问题”

**（一）`默认通道` 会不会显示给英文用户？→ 不会。**

服务端 `channel-utils.js` 里 `DEFAULT_CHANNEL_NAME = '默认通道'` 是一个**呈现值**，看起来会直接进 UI。但追下去：

1. 客户端的 `getDeclaredChannels()` 只取 **已声明**的通道（`list.filter(c => c && c.id)`），而默认通道的 `id` 是空串 —— **被过滤掉了**；
2. 设备页下拉框对默认通道用的是**哨兵值** `__default__`，模板里走 `{{'device.channels-filter-default' | translate}}`，**由前端自己的语言包出文案**；
3. `getChannelName()` 对默认通道显式返回空串。

→ **该中文常量不会出现在界面上**，无需修改。（保留它是因为它是既有 API 形状的一部分，改动无收益。）

**（二）服务端错误信息直接回显给用户，会不会是中文？→ 不会。**

客户端确实会把 `err.error.message` 直接弹给用户（`project.service`、`camera-*`、`calibration-*` 等 8 处）。但服务端产出的是英文（`Unauthorized!`、`view "…" not found` 等），所以**不会出现中文串到英文界面**。

**（三）`frango` 残留 → 已在上一轮处理**，剩 8 处均为 localStorage 键（台账 UI-9）。

## 13. 第九轮：绕开 headless 网络限制，拿到了真实画面的渲染证据（2026-09-29）

### 14.1 做法
