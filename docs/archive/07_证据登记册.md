## 4. 需要更正 Codex 的一处技术前提（E27）

**Codex 原话（评审第 281 行）**：「WAL 模式下，已提交数据可能仍在 -wal 文件中……所以不能把改后缀作为完整迁移方案。」

**实测结果**：该前提**在本项目当前配置下不成立**——
- `runtime/project/prjstorage.js:65-67`：`new sqlite3.Database(dbfile, ...)`，**未设置** `journal_mode`；
- `runtime/alarms/alarmstorage.js:45-48`：同上；
- 全库检索 `PRAGMA journal_mode`：**仅** `runtime/calibration/calibration-storage.js:158` 命中（`WAL`）。
- 佐证：`runtime/storage/sqlite/index.js:424-429` 专门清理 `-journal` 遗留文件，说明实际使用的是 rollback journal。

**但 Codex 的方法论结论仍然采纳**，理由有两条实测依据：
1. `calibration-storage.js:158` 证明本工程**已经有一处开 WAL**，说明该风险不是理论假设；
2. `runtime/storage/sqlite/index.js:484` 的归档滚动改名**只搬主库文件、不搬 `-wal`/`-shm`** —— 这是与 Codex 同源的**真实潜在缺口**，只是位置不在品牌迁移、而在 DAQ 归档滚动。

→ 结论：**技术前提更正，行动要求保留**。详见 `06_未闭环项台账.md` 台账项 **L-11**。
