## 一、总体结论

**架构方向正确，解耦设计成立，可以进入 Phase 2。** 但 Phase 2 启动前有 **2 个必须钉死的技术决策**（不钉死会直接违反架构铁律 #2「tagId 稳定」），另有 **1 个范围收窄** 和 **1 个产品优先级问题需老板裁决**。

评审文档里 8 个检查点逐条判定见第四节。

## 二、阻断项（Phase 2 启动前必须钉死）

### 【阻断-1】tagId 主键的跨库迁移 / 写回稳定性 —— 最高优先

架构铁律 #2 把 tagId 当作 11 类数据消费者的统一锚点（历史归档/实时报警/历史报警/标定/调度/报表/趋势/实时图表/配方/脚本/OPC UA 发布）。但 **tagId 当前怎么生成、迁移到 MySQL/PG/SQLServer 时能否保真、写回外库时会不会撞号，文档没钉死**。

Phase 2 一引入「写回」，平台就不再是 tagId 命名空间的唯一拥有者——外部系统也能产生/回写 tag。一旦迁移或写回过程中 tagId 被重生成、被截断、或与平台侧撞号，**11 类历史绑定全部断裂**，等于把铁律 #2 打破。

**要求**：Phase 2 开工前先定稿一份 ID 方案，明确：①tagId 不可变、全局唯一、跨库迁移逐字节保真；②写回外库时 tagId 命名空间隔离规则（平台前缀 / 独立段），杜绝撞号；③迁移工具校验「迁移前后 tagId 集合一致」的门禁。

### 【阻断-2】SQLite(同步) vs MySQL/PG/SQLServer(异步) 的阻抗不匹配

集成规划 §2.2 提出 `runtime/storage/sql.js` 用「同一套通用 SQL 后端」抽象 better-sqlite3 + mysql2 + pg。但 **better-sqlite3 是同步 API（现有 DAQ 性能路径依赖它），mysql2/pg/SQLServer 是异步（Promise）**。

强求一套抽象只有两条死路：要么全异步（把现有 DAQ 写路径整体改异步，牵动整个采集链，违反「改一处不动全身」）；要么同步/异步双路径（抽象名存实亡）。**「方言适配」解决的是 SQL 语法差异，解决不了同步/异步语义差异**——这是两件事，文档混为一谈了。

**要求**：Phase 2 开工前定稿存储接口的**执行模型**：建议 DAQ 写路径统一为异步接口、SQLite 后端内部用队列/worker 承接（对外异步、对内仍享 better-sqlite3 性能），而不是让调用方感知同步/异步差异。SQL Server 还需单列方言适配（IDENTITY/NVARCHAR/TOP/无 `INSERT OR REPLACE`）。

## 三、范围与优先级

### 【收窄】「可视化写回」是 Phase 2 最大风险面，建议拆两半

「可视化写回」（用户在界面里定义规则写到外部库）= SQL 注入面 + 方言漂移 + 事务/一致性 + 权限。它和「多后端读/存」是两件事，不该捆在一期。

**建议**：Phase 2 拆为 2a（多后端存储：把 DAQ 镜像到 MySQL/PG/SQLServer，**平台仍是唯一写者**，只读旁路）→ 2b（可视化写回：受限 DSL + 参数化绑定，**禁任意 SQL**，单独一期）。2a 风险低、能立刻验证「数据稳定」铁律在真多库下成立；2b 单独设计。

### 【老板裁决】Phase 2 多数据库 vs Phase 5 AI 分析的优先级

Phase 2 是**基础设施**，Phase 5 AI 分析（归档→RAG→领域门控→模型→结构化输出）才是**差异化卖点**。对一个「非程序员工控人员友好」且要可演示的 V1.0，先铺多库（工作量 2-3 周、对演示无感）还是先做单库 SQLite 下的「预测」闭环（可演示、直接打动人），是产品优先级问题，不是技术问题。**请老板拍板**。

## 四、8 个检查点逐条判定

| # | 检查点 | 判定 |
|---|---|---|
| 1 | 模块边界是否真解耦 | ✅ 方向对（旁挂/init/stop 独立/注册表）；存量 FUXA 是否有隐性耦合 → 留给 Codex 逐行审 |
| 2 | tagId 是否真零改动 | ⚠️ 设计成立，但 **未钉死 ID 方案**（见阻断-1），Phase 2 写回会暴露风险 |
| 3 | AI 走统一 API 读归档不碰物理库 | ✅ 正确，是「换存储后端零改动」的关键取舍 |
| 4 | 「通道是 tag 属性」有无隐患 | ⚠️ 设计合理；隐患在**存量代码是否仍把通道当容器**（Codex 逐行核）+ 通道级批量操作在 1000 tag 下的性能 |
| 5 | 品牌化 + 数据兼容方案 | ✅ 稳妥（运行时归一化 + .db 重命名 + VACUUM）；3 个技术保留项合规 |
| 6 | AI 视频「外部推理 + 平台接入」独立替换 | ✅ 成立；前提是把 `region∈0..1` + 事件 JSON 契约**冻结成稳定 contract**（A9 已暗示） |
| 7 | AI 分析「启用标记 + 模型可替换 + 中转站」完整 | ✅ 结构完整；需补 2 个细节：①「校准参数/打标结果」存哪（要纳入 Phase 2 迁移清单）②领域门控阈值需可配可校准 |
| 8 | Phase 2-7 优先级与风险 | ⚠️ 见第三节：多数据库应拆 2a/2b，且与 Phase 5 优先级需老板定 |
