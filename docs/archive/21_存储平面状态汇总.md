| 编号 | 缺陷 | 证据 |

| **D6-1** | 适配器用 `dt BETWEEN ? and ?` —— SQL 的 BETWEEN **两端闭**，即 `[from, to]`，契约要求 `[from, to)`。门面 `querySeries()` 自己补了一道过滤所以看不出来，但遗留路径 `getNodesValues()` 没有 → **报表窗口 `[00:00, 24:00)` 会带上 24:00 那一笔** | 反向验证注入 19 把 BETWEEN 放回去，用例立刻变红 |

#### D9 途中，我自己的守卫抓到了我自己的一个洞

backend-config-probe.js 的 setImmediate(...) 写在守卫**外面**，而 outFile 取的是 process.argv[2] ——

### D8 · PostgreSQL —— 已证实（真引擎）

本机 Docker 守护进程原本没起。把它拉起来之后：

| 步骤 | 结果 |
|---|---|
| npm run test:backends:up | PostgreSQL 18 容器起来了（改用本机已有镜像，省一次 400MB 拉取） |
| 契约套件 | **8/8 全过** —— 适配器第一次面对真引擎 |
| 能力矩阵 PostgreSQL 列 | 十轴**全部实测**填实，不再 unverified |
| 冻结待证实 | **12 格 → 8 格** |

**套件第一天就抓到两个真问题，都修了：**

1. **套件自己的上界不可移植**：ALL_TIME 的上界是 Number.MAX_SAFE_INTEGER。SQLite 存整数毫秒所以一直没事，
   而 pg 把它变成 Invalid Date，服务端直接拒绝（invalid input syntax for type timestamp）。**第二个引擎一上来就暴露** —— 这正是 D8 存在的理由。
2. **适配器把查询错误吞成了空数据**：query() 的 catch 返回 {rows: []}，于是「后端失败」和「没有数据」长得一模一样 ——
   而**消除这个混同正是查询契约存在的目的**。改为失败即失败（抛出去），只有未连接时才降级为空。

证实的记录方式也改了：在 unproven / delivered 之外增加 **provenOn** ——
**「被证实」是一次事件，不是机器状态**。机器上没有数据库是机器的属性，不是后端的属性。
