## 2. 测试基线：本次实测复现（比引用更严重的一个发现）

评审原文 L363-366 指出架构原文 L210 的"436 passing（含既存 2 条 Windows 环境失败）"不成立。
**本次我实际安装依赖并复跑了测试**（这是评审原文没有做、也声明没做的事）。结果**比 Codex 指出的更值得警惕**：

| 轮次 | 命令 | 结果 |
|---|---|---|
| 第 1 次 全量 | `npx mocha --recursive --timeout 10000 --reporter dot` | **429 passing, 2 failing** |
| 隔离运行 | `npx mocha --timeout 30000 --exit test/opcua-server/opcua-server.test.js` | **15 passing, 0 failing** |
| 重复运行 ×4 | `npx mocha --recursive --timeout 20000 --reporter dot --exit` | **437 passing, 0 failing**（4/4 一致） |

### 2.1 第 1 次的 2 个失败，**不是**文档所说的"Windows 环境既存失败"

失败栈（原文摘录）：

```
1) OPC UA server "before all" hook …
   Uncaught AssertionError: expected 64 to be below 60
      at Timeout._onTimeout (test/help/runtimeUtils.test.js:160:38)
2) … in addition, done() received error: TypeError: Cannot read properties of null (reading 'endpoints')
      at Object.init (runtime/opcua-server/index.js:180:24)
```

**根因（已定位到行）**：
- `test/help/runtimeUtils.test.js:152-162` 的 `Utils.endTime` 用例把断言放在 `setTimeout` 回调里，但**这个回调是异步的兜底，真正的`done()`来自外层**——断言在**测试已结束之后**才触发。
- 它抛出的未捕获断言（`expected 64 to be below 60`，阈值 `delay + 50` = 60ms）被 Mocha 归给了**下一个正在运行的** `before all` hook（OPC UA），于是同一次失败被报了两次（`done() called multiple times`）。
- 第二条错误的 `null.endpoints` 出现在 `opcua-server/index.js:180`。我**不把它断定为独立缺陷**：它要么是上述用例污染的连带结果，要么指向一个 `init` 与 `stop` 的竞态（`stop()` 在 `:200` 把 `server` 置空）。**隔离运行不复现**，故本次按"待复现观察项"处理，列入台账 **L-12**，**不写成缺陷**。
- **隔离运行 OPC UA 15/15 全过** → 证实这**不是** OPC UA 的缺陷，而是**测试卫生问题**（异步断言泄漏 + 共享模块级单例）。
- 同时说明：`expected 64 to be below 60` 是**时序抖动**——一个 10ms 的 `setTimeout` 在负载下逾 60ms，属于**典型 flaky 用例**。

### 2.2 因此，文档声称的"2 条 Windows 环境失败"**与实际失败原因不一致**

架构原文 L210 与 `02_PLAN_集成规划.md:786` 都把失败归因为"Windows 环境"。
本次实测：**失败原因是测试自身的 flaky 断言 + 用例间状态泄漏**，与操作系统无关（隔离即通过）。
这正是评审原文 L365 要求"明确失败命令及环境、是否正式豁免"的价值所在——**当前归因是错的，不能据此豁免**。

### 2.3 结论（精确表述）

**基线数字目前是"负载相关的双态"，不是唯一确定值**：同一套代码、同一台机器，全量运行出现过两种结果——
- **437 passing / 0 failing**（4 次连续运行一致，属稳态）；
- **429 passing / 2 failing**（第 1 次运行，当时另有编译/安装负载在跑）。

两次差异**全部落在同一条时序敏感断言**（`runtimeUtils.test.js:152-162`，阈值 60ms，实测 64ms）及其引发的用例间状态泄漏上，**与业务代码无关**。归一化验证：**隔离运行 OPC UA 15/15 通过**。

因此准确的结论有两条，且都支持 Codex：
1. **"437 passing"不能作为无条件稳定基线** —— 它在负载下会退化；一个会随时序抖动的基线，不能作为验收证据（→ 台账 **L-01**，处置见 §5 的 **P2-0**）。
2. **文档把失败归因为"Windows 环境既存失败"是错误归因** —— 真实原因是**测试自身缺陷**（异步断言泄漏 + 共享模块级单例），**与操作系统无关**（同一 Windows 机器隔离运行即通过）。错误归因会导致错误豁免（→ 台账 **L-02**）。

> 说明：本次复跑使用本机 Node **v24.19.0**（架构文档基线写作时使用 Node 20）。跨版本差异**不作为**本文结论依据——上述 flaky 与状态泄漏机制与 Node 版本无关。跨版本完整回归仍列入台账 L-02 待复核。

## 3. 八项意见逐条回应

### 意见 1｜解耦性：运行时隔离和副作用边界尚未闭合 — **A（含 1 项 B）**

| 子项 | 类别 | 回应 |
|---|---|---|
| ① 同进程争抢事件循环 | A | 接受 |
| ② deadband 与报警顺序 | A | 接受风险，**但成因与修法需更正** |
| ③ AI 回写 Tag 的副作用 | A | 接受，**且实测已发生** |
| ④ 驱动注册表状态 | A | 接受，**Codex 判断准确** |

**① 接受。** 需补"模块故障与资源隔离契约"（依赖/生命周期/超时/失败语义/资源所有权），以及"关视频、断网关、造慢查询"的故障隔离门禁。
**已实现部分（B 类）**：视频初始化失败**确实**不阻断采集——`runtime/index.js:99-101` 的 `cameras.init(...).catch(...)` 仅记日志；`cameras/index.js:24-34` 中 GB28181 与 AI 摄入各自 catch，注释明写"5060 被占不能带崩 runtime"。**但这只证明"失败不阻断"，不证明"过载不拖慢"** —— 后者仍属 A 类待补。
**同进程负载点已有现实证据**（非推断）：`runtime/opcua-server/index.js:530-535,549-551` 的 `refreshTags()` 每次遍历**全部已发布 Tag**，`tagPollMs` 默认 1000ms、下限 200ms；`runtime/index.js:608-626` 把设备值 `io.emit` 广播给全部前端。

**② 接受风险，更正成因。** 实测（见 `07_证据登记册.md` E01-E05）：
- 该死区是 **Tag 组装死区**（`device-utils.js:32-34`：小变化时 `value = oldValue`），**不是归档死区**；归档判定是另一个函数 `tagDaqToSave`（`device-utils.js:9-12`，用 `tag.changed`/`daq.interval`）。
- 被压平的值**写回 `varsValue`**（`modbus/index.js:832,838`），而**报警引擎读的正是这个值**（`alarms/index.js:308 → devices/index.js:213-215 → device.js:279`）。
- 推给浏览器的是**未经压平的完整 `varsValue`**（`modbus/index.js:176`）。
→ **Codex 举的例子（99→101、死区 10、阈值 100）在当前实现下确实可能漏报**；且存在"浏览器看到 101、报警判定看到 99"的**双视图不一致**。
→ **修法更正**：不是"把归档死区从报警链前移"，而是**明确死区语义分层**——死区只决定"是否产生新值／是否归档／是否推送"，**报警判断必须吃未经死区压平的瞬时值**。此项**先写入契约，改码留待 P2 单独批准**。

**③ 接受，且已发生。** 写 Tag 的真实入口：`cameras/fusion.js:217-224 writeEvent()` → `_setTag`；调用方 `cameras/ai/ai-service.js:179,203`（`alarmTagId` 置位/清零）。写回后**自动进入**：调度（`scheduler-service.js:33`）、OPC UA 发布（`opcua-server/index.js:518`）、实时推送（`runtime/index.js:627-629`）。
→ 架构原文 L164"AI 分析……不侵入 DAQ/报警/趋势既有链路"在**运行时并不成立**，必须定义受控写入边界。与意见 4 合并处理。

**④ 接受，Codex 判断准确。** `device.js:569-601 loadPlugin` 是一串 `if / else if`，**没有注册表**；新增驱动必须改核心文件。与架构原文 L45（写成落地机制）与 L231（列入 Phase 3）自相矛盾 → **改口径**：统一外壳已实现，**注册表未实现**。

### 意见 2｜数据稳定性：tagId 必要非充分 — **A（完全成立）**

**判定：全部接受。** 且实测证据**强于**评审原文的推断——Codex 是从文档缺口推断，实测发现代码中已有**具体实现形态**，其中 3 处为确定缺口：

| 子项 | 实测（`07_证据登记册.md`） | 类别 |
|---|---|---|
| ① 无独立于设备容器的 Tag 查找 | `devices/index.js:398-405 getDeviceIdFromTag()` 遍历 `activeDevices` **取首个命中** | 代码缺口：O(n)、重复 tagId 结果不确定、跨设备移动后**静默改解析** |
| ② 标识稳定 ≠ 语义稳定 | 无 数据类型/单位/质量码/标定版本 契约；标定库有版本表（`calibration-storage.js:159-171`）但 Tag 上**无"当前适用哪版标定"** | 契约缺口 |
| ③ 旧绑定回灌 | **全库无 `bindingRevision` 或等价代际标识** | 代码缺口（Codex 判断成立） |
| ④ OPC UA 外部身份 | `opcua-server/index.js:115-121,305-307`：`ns=<运行时索引>;s=<点分路径>`，路径含**设备名+Tag名**；tagId 仅在 `description` | 代码缺口 |
| ⑤ 工程库主键 ≠ 引用完整性 | 工程库为 `name TEXT PRIMARY KEY, value TEXT`；`tag-io.js:8-15` 导入**只增不删** | 接受，仍需补唯一性/不复用规则 |

**最强的一条佐证**：把 Tag 从设备 A 移到设备 B —— 即便 tagId 不变，**OPC UA 的 NodeId 会变**（路径含设备名），**`getDeviceIdFromTag` 的返回值也会变**。故架构原文 L120 的"tagId 不变 → 全部零改动"在**外部身份**与**设备树解析**两个维度上均不成立。

→ **补**：《Tag 身份与绑定生命周期契约》（生成/唯一范围/导入冲突/删除不复用、独立查找接口、`bindingRevision`、待执行写命令绑定目标版本、OPC UA 稳定 NodeId 与命名空间 URI、语义迁移规则）。
→ 验收必须覆盖老板列出的**全部消费者**，并**明示切换期允许的数据间断**——不能用"零改动"暗示"零间断"。

### 意见 5｜通道是 Tag 属性 — **C（部分接受）**

- **接受**"通道是 Tag 属性而非容器"的结构选择（`channel-utils.js:8-22` 已给出理由，且是老工程兼容成本最低的方案）。
- **接受** Codex 的反对部分：**不能**因为"Tag 只保存一个属性"就把连接职责散落到各个 Tag。通道若承载连接地址/串口参数/认证/超时/轮询周期，就必须有独立配置与生命周期。
- **实测佐证该担心的现实性**：`channel-utils.js:326-351 removeChannel()` 删除通道时把 Tag **重指派**，默认**回落到默认通道**。对"分组"语义合理，对"通信来源"语义**危险**——工业系统不应通过静默回退把 Tag 接到另一个来源。
- **同时保留**：计算 Tag / AI 预测 Tag 可能没有物理通道；冗余采集可能有多个候选来源。**不应强迫虚拟 Tag 伪装成物理设备 Tag**（架构原文未定义，需补）。

→ **补**：把 **Tag 身份 / 通信绑定 / 界面分组**三者分开定义；明确配置继承优先级、无通道老工程语义、删除通道与批量迁移行为、通道切换走统一绑定操作。

### 意见 6｜品牌化与数据迁移 — **C（含本次唯一 D 类）**

**接受部分（80% 成立）**：
- **"改名 = 迁移完成"不成立**，接受。**且实测更硬**：全库检索 `fuxap` / `renameSync`，**代码中根本不存在 `.fuxap.db → .scadiap.db` 迁移**；唯一 `renameSync` 命中是 `runtime/storage/sqlite/index.js:484` 的**归档滚动改名**，与品牌迁移无关。架构原文 L128/L208 的"数据迁移……本次完成"**缺代码证据**（详见 §6 裁决项 D6）。
- **品牌别名不能到处替换**，接受：运行时归一化只在 `device.js:36-38` 一处（`'FuxaServer'→'SCADIAServer'`），**导入导出、离线迁移、工程校验、插件加载若绕过该入口仍不兼容**。
- **多库一致性与中断恢复未定义**，接受；要求可复跑、可回滚的六步迁移流程与验收矩阵。

**不采纳部分（D 类，1 条）**：评审原文 L279-283 的技术前提——
> 「WAL 模式下，已提交数据可能仍在 -wal 文件中……所以不能把改后缀作为完整迁移方案。」

**实测**：**本项目主库未启用 WAL**。`prjstorage.js:65-67` 与 `alarmstorage.js:45-48` 均为 `new sqlite3.Database(...)`，**未设置 `journal_mode`**（SQLite 默认 rollback journal）；全库 `PRAGMA journal_mode` 检索**仅 1 处命中**——`calibration-storage.js:158`（校准库）。佐证：`sqlite/index.js:424-429` 专门清理 `-journal` 遗留文件。
→ 因此"改后缀可能丢已提交事务"**在当前配置下不成立**，该条**不采纳**。

**但行动要求保留**（这正是"分类要准、处置要稳"的意义）：
1. `calibration-storage.js:158` 证明本工程**已有一处开 WAL**，风险非纯理论；
2. `sqlite/index.js:484` 的归档改名**只搬主库、不搬 `-wal`/`-shm`** —— 这是与 Codex 同源的**真实潜在缺口**，只是**位置不在品牌迁移、而在 DAQ 归档滚动**。

→ 结论：**技术前提更正，行动要求保留**，并写入《可回滚数据迁移规范》与台账 **L-11**。

### 意见 7｜AI 视频外部推理 — **C（部分接受）**

- **接受**"外置推理是正确边界"（架构原文 L48）。
- **① 坐标系：接受，且是真实风险。** `ai/normalize.js:64-68 normalizeRect(rect,width,height)` 直接按传入尺寸除算；尺寸取自 payload 或**配置默认值**（`:158-159`）。若模型输入是 ROI 裁剪或 letterbox 缩放后的画面，**输出仍在 0..1 但语义不同**，平台会**静默框错且不报错**。适配器必须负责还原到约定的**原始画面坐标系**，并记录帧尺寸/ROI/变换版本。
- **② 时间对齐：接受。** 5s TTL（`ai-service.js:25,157`）从**平台收到消息**起算，无法回答"框属于哪一帧"。需定义 cameraId、流会话 ID、帧标识/采集时间、事件时间与时间基准。
- **③ 框流 / 业务事件 / 健康状态必须分开：接受。** 与意见 4 同源；尤其**健康状态**：推理服务失联**不能被解释为没有异常**。
- **④ 模型能力不等价：接受。** Seek/Flow/VR/Go 是不同能力，共用接入框架 ≠ 可互换。按**能力**定义适配器契约（输出能力、时序/会话状态、标签体系、坐标约定、模型版本与健康状态），标签映射与阈值校准放在适配层。
