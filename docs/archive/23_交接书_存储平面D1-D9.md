## 2. D8 做了什么（这是本窗口最有价值的产出）

把 Docker 拉起来之后，PostgreSQL 从「纸面」变成「证实」：

| 项 | 结果 |
|---|---|
| 契约套件 | **8/8**（实例契约、存取往返、未知 tag 空列表、半开区间两侧、窗口外为空、关库重开仍持久、getDaqMap 归属） |
| 能力矩阵 PG 列 | **十轴全部实测**（durability/atomic-batch/ts-range/ts-aggregate/schema-evolution/binary-object/auth-tls/concurrent-writers = yes；retention/embedded-zero-ops = no） |
| 冻结待证实 | **12 格 → 8 格** |

**套件第一天就抓到两个真问题**（都已修）：

1. **套件自己的上界不可移植**：`ALL_TIME` 上界是 `Number.MAX_SAFE_INTEGER`。SQLite 存整数毫秒所以一直没事，
   而 pg 把它变成 `Invalid Date`，服务端拒绝（`invalid input syntax for type timestamp`）。改成十年的时间戳。
2. **适配器把查询错误吞成了空数据**：`postgresql/index.js` 的 `query()` catch 返回 `{rows: []}` → 「后端失败」与「没有数据」长得一样，
   而**消除这个混同正是查询契约存在的目的**。改为失败即失败；只有未连接时才降级为空。

**新增的架构概念：`provenOn`。** 在 `unproven` / `delivered` 之外，每个后端可以记录**一次证实事件**
（`provenOn: 'PostgreSQL 18 (docker compose), contract suite 8/8'`）。守则拒绝：
称为 delivered 却没有证实记录的、声称已证实而 registry 没有记录的、unproven 却带 provenOn 的。
**「机器上没有数据库」与「后端未被证实」从此是两件事。**

## 3. 当前阻塞（精确、可复现）

### B-1 TDengine 客户端库拒绝我们的参数形状（阻塞 D9 证实）

容器是好的：`scadia-test-tdengine` Up (healthy)，6041/6030 已映射。但 `@tdengine/rest` 3.0.2 的 `connect()` 对所有尝试形状都失败：

```
{ host:'127.0.0.1', port:6041, user, passwd }        -> Invalid URL
{ url:'http://127.0.0.1:6041', ... }                -> Invalid URL
{ scheme:'http', host:'127.0.0.1', port:6041, ... } -> Invalid URL
{ host:'http://127.0.0.1', ... }                    -> Only HTTP(S) protocols are supported
```

线索：`dist/main/index.js:39` 用 `scheme://host:port+path` 拼 URL；默认选项在 `:267` 是 `{ path:'/rest/sql/', scheme:'http', user:'root', passwd:'taosdata', host:'127.0.0.1' }`（**没有 port**）；`:62` 又对 `this.uri.url` 做 `new URL(...)`。
**下一步**：读该文件的构造顺序，或**换用官方 `@tdengine/client`（原生连接 6030）**，或直接用 REST 接口 `POST /rest/sql`（curl 可先验证引擎本身没问题）。
契约套件已就位，修好客户端后**只需 `npm run test:contract`**，不需要改测试。

## 4. 新窗口必须知道的三条教训（都是我踩过的）

### 教训 1：错判要更正到档案里，不要悄悄改

本窗口早先报告「UI 选 InfluxDB 1.8 → 静默落进 SQLite」。**该结论是错的**：我只实测了「字符串会落进 SQLite」，
**没有验证界面到底发什么**。查证后：模板绑的是枚举**成员名**（`[value]="type.key"`，`EnumToArrayPipe` 的 key 取 `Object.keys`），
界面实际发 `influxDB18`，服务端一直认识它。

处置：更正写进 `known-debt.js`、`06_未闭环项台账.md`、`21_存储平面状态汇总.md`；守卫从「两端枚举看起来一样」
改成**「两端能发出的每一种写法都必须解析得到」** —— 后者才是活路径的保证。**不要重犯。**

### 教训 2：守卫只查同步副作用 = 没查

`backend-config-probe.js` 的 `setImmediate(...)` 写在守卫**外面**，`outFile` 取 `process.argv[2]` ——
**在 mocha 下就是 spec 路径**。只要 require 它，下一个 tick 就把 JSON 写到正在跑的测试文件上。**它真的发生过。**

现在 `scannerContract.test.js` 的检查是**子进程 + 哨兵**：每个 helper 独立进程加载，`process.exit` 被陷阱替换，
`argv[2]` 指向哨兵路径，stdout 与哨兵文件同时盯。**任何新 helper 都必须惰性；异步副作用也逃不掉。**

### 教训 3：守卫必须读代码，不能读注释

结构守卫最初读原文，于是 SQLite 适配器**解释自己为什么不再用 BETWEEN** 的注释把它判成违规，
而 PostgreSQL 适配器换成 `BETWEEN` 的注入反而抓不到（当时它只查 `unproven` 后端，而 PG 已变成 delivered）。
现在：守卫读 `arch.stripComments()` 后的源码，且**检查所有交付后端**（不只 unproven）。

## 5. 这套东西的运作方式（新窗口照着做，别自创）

1. **单一来源 + 生成物**：`19_...json` → 生成 `19_...md`；`runtime/storage/contract.js` → 生成 `22_契约06...md`。
   两者都由守卫逐字节比对，**手改必红**。重新生成：`ARCH_MATRIX_UPDATE=1` / `ARCH_CONTRACT_UPDATE=1` / `ARCH_SNAPSHOT_UPDATE=1`。
2. **钉住（pin）= 精确集合**：`_support/known-debt.js` 里每条都带证据与关闭条件。
   新增违规立即红；**修好后不删钉也红** —— 所以钉不会比缺陷活得久。
3. **反向验证**：`npm run test:architecture:reverse` 对每条规则注入一次故意违规，要求**拥有该规则的那条用例**变红、
   且复原后重跑变绿。它有**全树快照 + 自动修复**，注入毁不掉正在验证的东西。加规则就要加注入。
4. **没跑 ≠ 通过**：契约套件的覆盖守卫强制「能跑的后端」由**夹具文件推导**，不能跑的必须写明原因与归口。
   未证实的后端**不可被用户选择**（除非它早已交付过 —— `offered: true`）。
5. **加一个后端的完整动作**：写 `runtime/storage/<id>/index.js` + 注册表一条 + 矩阵一行能力证据 + 一个夹具。
   交付时启用只是 `settings.daqstore.type` 一个值。
