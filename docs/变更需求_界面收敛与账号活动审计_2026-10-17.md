## 1. 背景与目标

现场使用「统一 AI 分析」时发现：该页默认模块是 `SCADA / DAQ`，目标是「当前异常」，右侧证据列出一批**与本项目无关的相机原生项**（连接状态、区域入侵、遮挡、移动侦测、视频丢失、视频篡改…）。本项目实际交付的是**八种算法（V1–V7 + T1）**。

用户要求：
1. 「统一 AI 分析」页**只呈现我们的八种算法**，不显示无关模块与无关证据。
2. 「每一页都这样」——**无关的页面/内容不做、不显示**，例如报警、报表这类与八算法无关的业务。
3. 在「报警」或「报表」中加入**账号活动记录**：什么时间、哪个账号登录、注销、退出。
4. 上述改动**先经审核**，再据此重写两份 Word 说明书。

## 3. 变更项 A：统一 AI 分析页只呈现八种算法

### A.1 现状（可核对证据）

| 事实 | 位置 |
|---|---|
| `/analysis` 页是 iframe 外壳，指向服务端 `/ai-analysis` | `source/client/src/app/analysis-workspace.component.ts`（routing：`app.routing.ts:44`） |
| 分析页 UI 在服务端独立 HTML（52 行） | `source/server/ai-analysis.html` |
| 模块列表来自 `GET /api/analysis/modules` | `source/server/api/analysis/index.js:151` |
| 模块定义 `MODULES`（共 11 个） | `source/server/api/analysis/evidence.js:10-21` |
| 八种算法定义 `SCENE_TARGETS` = V1…V7、T1 | `source/server/api/analysis/scene-evidence.js:3-6` |
| 前端**已**对 video 模块做目标过滤，但**模块下拉仍列全部**、默认非 video | `ai-analysis.html:40`（过滤）、`:51`（仅在存在 video 时才设为默认） |

`MODULES` 当前包含：`scada`、`mes`、`ems`、`video`、`alarms`、`recipes`、`schedules`、`reports`、`calibration`、`devices`、`platform`。
其中**属于本项目**的只有 `video`：内含 `all_scenes`（八场景综合 / 报表窗口）、`scene_event`（单事件）、以及 `SCENE_TARGETS` 展开的 `V1…V7、T1`。
`video` 内还挂着两个**旧接口**目标：`detection_freshness`、`event_counts`（备注明写"不代表八场景记录"）——建议一并移除。

### A.2 目标

- 模块下拉**只有八场景**（可保留单一标题如「八场景与 AI」）。
- 目标下拉**只有**：八场景综合、单事件证据分析、V1、V2、V3、V4、V5、V6、V7、T1。
- 打开页面**默认**即为「八场景综合」，证据区不再出现 DAQ / 相机原生的无关条目。
- 不改变底层证据筛选与「证据不足不请求模型」的既有语义。

### A.3 方案

**首选（服务端白名单，可回滚）**
- 在 `evidence.js` 增加一个受开关控制的收敛出口，例如 `ANALYSIS_FOCUS=scenes`：
  - `MODULES` 仅导出 `video` 一项；
  - `video.intents` 只保留 `scene` / `scene_overview` / `scene_event` 三类，删除 `detection_freshness`、`event_counts`；
  - 其余模块（scada/mes/ems/alarms/recipes/schedules/reports/calibration/devices/platform）在 `scenes` 模式下**不下发给前端**（`/api/analysis/modules` 只返回收敛后的列表）。
- 这样做的好处：单一数据源，前端无需再判断；开关关闭即回到现状，便于回滚。
- 注意：`/api/analysis/test`（"测试连接"）内部固定使用 `platform` / `runtime_status`。收敛后**该按钮仍需可用**（它不走用户可见的模块下拉），实现时要保证它不因白名单而失效。

**备选（仅前端过滤，改动最小）**
- 只改 `ai-analysis.html`：渲染模块下拉时过滤掉非 `video`，并把默认值强制为 `video`。
- 缺点：服务端 `/api/analysis/modules` 仍对外暴露全部模块，语义没有真正收敛；前端遗漏一处就会回退。

> 建议取**首选**；若审核要求把改动面压到最小，可取备选并记录限制。

### A.4 影响面

- 消费 `/api/analysis/modules` 的其他客户端（如 `scene-board`、`workspace-shell`）需回归，避免出现"找不到模块"的空态。
- 分析历史与"已保存的场景分析"记录不受影响（按 `module+intent` 存的是历史文本）。
- MES / EMS 页面的 AI 分析能力会随之隐藏——若将来需要，可通过开关按需恢复。

### A.5 验收标准

1. 打开 `/analysis`：模块下拉**只有一项**；目标下拉只有上列 10 项；默认选中「八场景综合」。
2. 证据区不出现连接状态 / 区域入侵 / 遮挡 / 移动侦测 / 视频丢失 / 视频篡改 / 今日次数等条目。
3. 选择 V1–V7、T1 时能读到对应场景的最近 30 条事件与复核状态。
4. 「测试连接」仍可返回模型连通结果，且**不回显密钥**。
5. 无证据时返回 `evidence_insufficient`，**不请求模型**（既有语义保持不变）。

## 5. 变更项 C：账号活动审计（登录 / 注销 / 退出）

### C.1 现状（可核对证据）

| 事实 | 位置 |
|---|---|
| 登录成功：`POST /api/signin` | `source/server/api/auth/index.js:149` |
| 登录成功发事件 `access:login`（含 `username`、`fullname`） | 同上 `:170` |
| 注销：`POST /api/signout`（清 Cookie） | 同上 `:248` |
| 注销发事件 `access:logout` | 同上 `:255` |
| 刷新令牌：`POST /api/refresh` | 同上 `:193` |
| **是否存在持久审计表** | **不存在**（全 `api/` 目录检索 `audit` / `loginHistory` 无结果） |

也就是说：登录/注销目前**只发内存事件**，进程重启即丢失，页面也无处可查。这正是要补的部分。

### C.2 术语定义（重要，含诚实限制）

| 动作 | 判定 | 限制 |
|---|---|---|
| **登录** | `POST /api/signin` 校验通过 | 可精确记录 |
| **登录失败** | 同上，校验未通过 | 可记录（建议记录，属安全关切）；注意不要记录口令 |
| **注销** | 用户主动 `POST /api/signout` | 可精确记录 |
| **退出** | 关闭标签页 / 关闭浏览器 / 会话超时 | **服务端无法可靠感知"关页面"** |

**关于"退出"的诚实说明：** 浏览器关闭时服务端收不到任何请求。要做到可核对，建议：
1. 前端在页面卸载时用 `navigator.sendBeacon('/api/session/exit')` 上报"退出"（尽量送达，但不保证）；
2. 若未收到上报，则由**会话超时/令牌过期**在服务端补记一条 `session_timeout`，与用户主动退出区分开；
3. 两者在审计表中用**不同的动作码**区分，避免把"超时"写成人"主动退出"。

如果审核不接受"退出"存在不可靠性，可选做法是**只记录登录、登录失败、注销**，把"退出"标为"无法保证"，在页面与手册中如实说明。

### C.3 落点决策：放"报表"（推荐）还是"报警"

**推荐：放报表。** 理由：
- 这是**按时间顺序的台账**，与报表"时间范围查询 + 导出"的能力天然匹配，不必新建页面。
- 报警带有 `active / cleared / acknowledged` 的**状态机与计数语义**；把登录/注销塞进报警会污染报警统计与确认流程，语义错误。

**备选：放报警（作为"系统事件"分类）。** 传统组态软件常把登录/注销显示在"报警/事件"窗口。若采用，必须满足：
- 账号活动**独立成类**，**不计入**报警数量、不参与报警确认、不出现在报警趋势里；
- 界面上与设备报警**视觉分组**，避免误读为现场异常。

**建议的折中**：主体放**报表**；仅把**登录失败**作为一条可选的安全事件进入报警（需审核同意）。

### C.4 建议实现

- **存储**：新建独立 SQLite（例如 `_appdata/accounts.db`，与既有 `users.scadiap.db` 分开，便于单独保留与备份）。
  - 建议字段：`id`、`at`（毫秒时间戳）、`username`、`fullname`、`action`（`login` / `login_failed` / `logout` / `session_timeout` / `exit`）、`result`（`ok` / `denied`）、`clientIp`、`userAgent`（截断）、`sessionId`（可空）。
  - **禁止**记录口令、完整 token、Cookie。
- **服务端**：在 `auth/index.js` 的登录成功/失败、注销处写入审计；新增 `POST /api/session/exit`（仅记录当前会话退出）；新增查询接口 `GET /api/accounts/activity?from&to&username&action`（管理员权限、分页、上限保护）。
- **前端**：在报表中新增"账号活动（登录 / 注销 / 退出）"数据源与报表项，列为：时间、账号、姓名、动作、结果、来源 IP；支持时间范围筛选与导出（复用既有报表导出）。
- **保留期**：与既有 `logs` / `alarms` 保留策略对齐，需在工作站设定容量与归档（见待决点 D4）。
- **权限**：审计读取**仅管理员**；普通账号 403。

### C.5 验收标准

1. 用 A 账号登录 → 报表中新增一条 `login`，时间/账号/动作/结果正确。
2. A 主动注销 → 新增一条 `logout`。
3. A 关闭页面（或超时）→ 记录为 `exit` 或 `session_timeout`，且与 `logout` **可区分**。
4. 登录失败（错口令）→ 记录 `login_failed`，且**不含口令**。
5. 审计表**不存**口令/token/Cookie；导出文件同样不含。
6. 普通账号读取审计接口返回 403；管理员正常。
7. 服务重启后，历史审计**仍在**（已持久化）。

## 7. 风险、回滚与边界

| 风险 | 说明 | 缓解 |
|---|---|---|
| 模块收敛影响其他页面 | 有页面共用 `/api/analysis/modules` | 收敛前后各跑一次页面回归；用开关可回滚 |
| 菜单裁剪影响习惯 | 现场可能已习惯某个入口 | 开关控制；保留路由 |
| "退出"不可靠 | 关浏览器无法服务端感知 | 用 beacon + 超时补记，并**如实标注** |
| 审计写入放大 | 高频失败登录可能刷表 | 限流/去重；设保留期 |
| 审计含敏感信息 | IP、User-Agent | 只存必要字段；不存口令/token |

**回滚**：所有收敛项走开关；审计为**新增**独立库，关闭功能即可停止写入，不影响既有库。

**边界（本次不做）**：
- 不改八场景算法本身、不改门口标定逻辑、不改测温链路。
- 不删除报警/报表的既有功能，只做菜单隐藏与"账号活动"新增。
- 不重写 Git 历史、不 force push、不动 master。
