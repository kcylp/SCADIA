**这说明什么**：这些文件是**压缩产物，压缩时把上游的版权头连带去掉了**。压缩本身不违法，但**再分发 MIT/BSD 类代码时，许可与版权声明必须随产物一起提供**——所以这是一个**真实的分发合规缺口**，而不是"看起来不整洁"。**这一条我不替任何人打包票，只如实记录实测结果。**

## 3. 发版前必须完成的动作（清单）

1. **取回许可原文**：为 §2 每个组件取回其 LICENSE 文件（含版权行与年份），放进 `源代码/client/src/assets/lib/<组件>/LICENSE` 或统一放进 `THIRD-PARTY-LICENSES/`。
2. **补齐被剥离的头**：对 22 个无声明文件，**在其产物旁**放许可文件即可（**不要改压缩产物本身**——改压缩产物等于自己维护一份 fork）。
3. **保留改名映射**：`scadia-editor.min.js` 与上游 SVG-edit 的对应关系**要写进清单**，否则"这是我们的代码还是别人的代码"无从回答。
4. **确认 PDF 字体**：`pdfmake` 与仓内字体文件的许可（**字体常是独立授权**，与代码许可不同）。
5. **确认 TDengine 边界**：见 `21_TDengine许可边界裁决.md`（引擎 AGPL / 连接器 MIT 是两件事，**实测引擎未进交付物**）。
6. **CI 检查**：把"`assets/lib` 里每个组件目录下有许可文件"写成一条守卫（**目前没有**，见 §4）。

## 4. 尚未建立的守卫（诚实记录）

**没有**任何自动化检查会告诉你"新增了一个 vendored 组件却没有带许可"。这与 `uiConsistencyR1R2R3`（批次 52 才建）是同一类缺口：**规则存在、守卫不存在**。

建议在发版流程定稿后补一条：列出 `assets/lib` 下的每个组件目录，要求每个目录内存在 `LICENSE*` 或清单里有对应条目。**现在不建**，因为它会立刻为 22 个文件报红，而修它们需要先把许可原文取回来——先有文件，再有守卫。
