> 交付物 **D3**（存储平面）。铁律 ②「接口冻结前做纸上实现」、③「填空失败就修接口，不打补丁」。

## 0. D3 到底要干什么

D4 要把五个域契约冻死。冻结之前必须先证明：**这套接口在真实后端上真的填得进去。**
所以 D3 不是写代码，是拿三方各自的官方文档，把接口的每一个操作走一遍，然后老实报告
哪里走不通。走不通的地方**改接口，不打补丁**。

## 2. 被填空的接口

### 2.1 适配器实例契约（D1 已冻结）

```
setCall(fncGetProp)                 -> 返回写入函数
addDaqValues(tagsValues, deviceName, deviceId)
getDaqValue(tagid, fromts, tots)    -> [{ dt, value }]
getDaqMap(tagid)                    -> { [tagid]: true }
close()
```

可选：`init()`（influxdb / tdengine / questdb 有，sqlite 没有）、`addDaqValue()`（sqlite / influxdb 有）。

### 2.2 门面查询契约（runtime/reporting 与 contract 10）

```
querySeries(tagIds, fromTs, toTs, options)
  -> { contractVersion, requested{interval:"[from,to)"}, status{}, series{}, gaps{}, resolution{} }
```

半开区间 `[from, to)`、不插值、缺口显式上报、超限显式报错。这是**契约要求**，不是后端可选。

## 3. 逐后端走接口

### 3.1 SQLite —— 全部填得进去（实测）

嵌入式、本机可运行，因此十轴全部由 `test/architecture/_support/capability-probe.js` 真机测量，
并用产品自己的 schema 走了一遍。要点：

| 轴 | 结论 | 实测细节 |
|---|---|---|
| durability | yes | 写入 → 关闭 → 重开 → 读回，值一致 |
| atomic-batch | yes | 两行 ROLLBACK 后剩 0 行，COMMIT 后剩 1 行 |
| ts-range | yes | `WHERE id=? AND dt>=? AND dt<?` 在 [10000,20000) 取到 10 行，**正好是契约要的半开区间** |
| ts-aggregate | yes | 分桶 GROUP BY + MIN/MAX/AVG，10 个桶 |
| retention | **no** | 无 TTL 构造；产品靠删整个归档文件（sqlite/index.js:700 checkRetention） |
| schema-evolution | yes | 有数据的表上 ALTER TABLE ADD COLUMN 成功 |
| concurrent-writers | **no** | 第二个并发写者 `SQLITE_BUSY: database is locked` |
| embedded-zero-ops | yes | 直接开文件，无服务端、无端口、无账号 |
| binary-object | yes | BLOB 往返 6 字节完全一致 |
| auth-tls | **no** | 本地文件没有账号，也没有可加密的传输；访问控制只有文件系统权限 |

**对契约的约束**：默认后端不提供 TTL、不支持多进程写、没有传输安全。D4 不得把这三样写成必需。

### 3.2 TDengine —— 走得到，但有一条走不通（官方文档）

逐操作走：

| 接口操作 | 能否填 | 依据 |
|---|---|---|
| `create(...)` 建库建表 | 能 | `CREATE DATABASE IF NOT EXISTS` / `CREATE STABLE IF NOT EXISTS` 均在文档中 |
| `setCall` | 能 | 与后端无关，纯回调装配 |
| `addDaqValues` 写 | **能，但没有事务** | 文档口径：事务机制只作用于**元数据**，业务数据「针对表的操作都是以队列方式逐个进行」 |
| `getDaqValue` 读 | 能，且天然半开区间 | 文档支持 `WHERE tag_id=? AND dt>=? AND dt<?` |
| `getDaqMap` | 能，但语义是空的 | TDengine 只有一个库、不按设备分片，只能恒返回「归我」 |
| `close` | 能（空实现） | 连接由驱动层管 |
| 保留期 | **后端能，现有适配器不能** | 文档有 `KEEP` / `DURATION` / `RETENTIONS` 与表级 `TTL`；但代码里是 `//TODO add retention` |
| 二进制对象 | 后端能（BLOB ≤16MB，限普通数据列） | 文档明列；但现有表把值定成 `tag_value BINARY(20)` |
| 鉴权 | 部分 | `CREATE USER ... PASS` / `SHOW USERS` / `GRANT` 开源版可用；官方同页注明进阶用户管理需企业版 |

### 3.3 达梦 —— 只走到一轴（官方手册）

| 接口操作 | 能否填 | 依据 |
|---|---|---|
| 事务 | **能，而且是完整 ACID** | 官方手册原文：「DM 把一个事务的所有 SQL 语句作为一个整体，即事务中的操作，要么全部执行，要么一个也不执行」，并提供 `COMMIT` / `ROLLBACK` |
| 其余各轴 | **未取证** | 达梦官方手册站是 SPA，部分内容只以 PDF 发布，本轮只取到事务一轴的官方引用 |

达梦其余各轴留 `unverified`，由 **D10** 离线取得官方手册后填入。宁缺勿编。

## 4. 填空失败清单 —— 本轮的真正产出

> 按铁律 ③：下面每一条都指向**接口/契约的改法**，不是补丁。D4 冻结前必须逐条落地或逐条驳回。

| 编号 | 走不通的地方 | 证据 | 对接口/契约的要求 |
|---|---|---|---|
| **F-1** | TDengine 对业务数据**没有事务**，而 Event 域要求「多行原子提交、失败整体回滚」 | TDengine 官方：事务只作用于元数据；达梦官方：完整 ACID | **二选一**：契约不要求原子多行提交；或 Event 域不落在时序后端。→ 登记为 O-4，D4 裁决 |
| **F-2** | 现有 TDengine 适配器建库时**丢弃了保留期** | `tdengine/index.js:36  //TODO add retention`；而文档明确有 KEEP/DURATION/RETENTIONS | 保留期必须是**适配器接口的一部分**，不能靠各后端自觉。→ D5/D9 |
| **F-3** | 现有 TDengine 表把样本值定成 `tag_value BINARY(20)`，与后端 16MB BLOB 能力不符 | `tdengine/index.js:38`；文档：BLOB ≤ 16,777,212 字节 | Object 域若落在 TDengine，schema 必须改；契约需说明「值列宽度由后端决定」还是「由契约钉死」。→ D4/D9 |
| **F-4** | `getDaqMap` 在 TDengine 上是**恒真空实现**，它存在只是因为 SQLite 按设备分片 | `tdengine/index.js:110-114` | 这个方法把 SQLite 的存储布局泄漏进了公共接口。→ D4 要么给它真语义，要么删掉 |
| **F-5** | `addDaqValues` **每个标签一条 INSERT、且不 await**，失败只写日志、调用方拿不到 | `tdengine/index.js:46-76`；与已登记的 A-08 同类 | 写入接口必须能**回报失败**。批量写是否原子（见 F-1）必须由契约明确。→ D4/D5 |
| **F-6** | `create()` 首参在 sqlite 叫 `data`、在其余叫 `settings`，且参数个数 4 vs 3 | D1 快照 + A-05 | 适配器签名必须先统一再让三个后端去填。→ D5 |

### F-1 为什么是这一轮最重要的一条

SQLite 有事务，达梦有事务，**TDengine 没有**。

这意味着「报警/事件历史一次提交、要么全成要么全不成」这条诉求，在三个目标后端里
**有一个根本满足不了**。如果 D4 把原子性写进 Event 域契约而不区分后端，D9 的填空必然失败，
而那时候的补救就只能是打补丁——正是铁律 ③ 要避免的。

现在发现，成本是一句话；D9 发现，成本是重做契约。
