三、运行架构

3.1 进程拓扑（四进程）

进程端口/形态职责生命周期

3.2 三条数据流

  • 视频流：相机 RTSP → ffmpeg（nobuffer/low_delay/tcp）→ 代理 :1886 → 页面 svg image。画面脚本每秒幂等钉住 href（每窗唯一 ?c=wN），看门狗每 10 秒对 /stats 核对自己在线，断流自动换址重连（Chrome 对断掉的 MJPEG 永不自动重连，必须主动自愈）。
  • 事件流：相机 alertStream → 桥接器（事件字典翻译 + debounceMs 防抖 + 当日/累计计数落文件）→ 平台报警/计数；围栏状态写 _images/ai-fence.json 供画面高亮；报警同时经 ISAPI 抓拍存档（20 秒节流/200 张/7 天）。
  • AI 流：RTSP 子码流 → YOLOv8 推理 → 高频写 _images/ai-tracks.json（静态文件，画面 250ms 读，不受平台限流）+ 低频 0.2Hz POST /api/ai/events。

3.3 关键机制（为什么这么做）

  • CLIENT 脚本模型：平台每秒重跑工程里的 CLIENT 脚本。因此脚本必须幂等；跨帧状态挂 window；禁止 setInterval（热更新后旧函数会被旧定时器一直调用 —— 实测踩过）；改脚本必须 bump 版本号作废旧状态。
  • 限流铁律：平台全站 1000 次/5 分钟。高频数据一律走 /_images 静态文件；必须走 API 的（如 /api/alarms）节流 5 秒起步。
  • 热更新边界：POST /api/project 灌入只对新打开的页面生效；已开页面要 Ctrl+F5。
  • 全屏：requestFullscreen（浏览器栏+任务栏退场）+ CSS 三箭（藏 .header、--header-height:0、.home-container-nav top:0）才回收满幅空间。
  • PTZ 步进：变倍/聚焦是相机上的连续资源，move 之后必须有人发 stop。服务端拥有收尾权（ms 步进 + 到点必发 stop），前端只负责单击/按住/松开的语义。
  • 登录态：真实登录后 token 在 sessionStorage.currentUser（不在 localStorage）；画面脚本取 token 必须先查它。

3.5 当前关键参数

  • hmi.layout.start = v_zc_g1（默认落地 AI 检测）；navigation.mode = void（平台侧栏不出现）
