# 03 核查与风险报告

> 目的：让评审者回答一个问题——**这套代码是"能接手的工程"还是"屎山"**。
> 方法：以代码为准逐模块核查，关键结论**在运行实例上复现**。每条缺陷给 `文件:行号` + 触发条件 + 后果 + 等级。
> 等级定义：**P0** = 会导致用户看见"坏了"（白屏/打不开/数据不显示）；**P1** = 会误导或让维护变危险；**P2** = 债务/一致性。

## §2 已复现缺陷清单

### P0-1 服务端 `SHELL_ROUTES` 与前端路由表不同步 → 刷新即 404 白屏

- **位置**：`server/main.js:446-481`（路由表定义在 `:446-462`，挂载在 `:479-481`）。
- **机制**：这张表是**唯一**会把客户端路由回以 `index.html` 的地方——`app.use(BASE_PATH + shellPath, express.static(httpStatic))`，即"把静态根挂在子路径上"。不在表里的路由，只有在应用内点击（Angular pushState）时才走得通；**刷新、书签、直接粘 URL、弹窗打开**都会打到服务器拿 404，浏览器画出来就是白屏。
- **实测（修复前）**：`/alarms`、`/messages`、`/notifications`、`/scripts`、`/recipes`、`/reports`、`/language`、`/logs`、`/events`、`/mapsLocations`、`/flows`、`/apikeys`、`/userRoles`、`/arMarkers` 共 **14 条**返回 404，`document.querySelector('app-root')` 为 `null`，无任何控制台错误提示。
- **后果**：操作员在"实时报警"页按 F5 → 白屏，且看不出原因。
- **修复**：把表补齐到 29 条（与 `client/src/app/app.routing.ts` 对齐）。修复后实测 27 条客户端路由全部 200 且含 `<app-root>`。
- **为什么没被发现**：**没有任何测试断言这两张表一致**（`server/test/` 全库 grep 无 SHELL_ROUTES 断言）。
- **建议**：加一条架构测试，从 `app.routing.ts` 解析出路由清单并与 `SHELL_ROUTES` 双向比对。

### P0-2 工程 `layout` 行不完整 → `/api/project` 直接 4xx，前端整站空画布

- **位置**：`server/runtime/project/index.js:1184`（`if (result.hmi.layout && result.hmi.layout.navigation.items)`）与 `:1193`（同理取 `layout.header.items`）。
- **机制**：**只判 `layout` 存在，就直接取 `layout.navigation.items` / `layout.header.items`**。工程里只要有一行 `layout` 但缺 `navigation` 或 `header`，这两行必抛 `TypeError`。
- **实测**：工程原本没有 `layout` 行（`general` 表只有 `version`），所以这条路径从未被走到；本次给它写入 `{"start":"v_zc_g1"}` 后，`/api/project?views=lazy` 返回 **400**，服务端 `scadia-err.log`：`api get project: TypeError: Cannot read properties of undefined (reading 'items')`，前端表现为 `SCADIA load error HttpErrorResponse` + 页面只剩页眉、画布全空。
- **后果**：**任何"给工程配起始画面"的正常运维动作都可能把整站打挂**，而且错误信息在浏览器侧完全不可读。
- **修复**：`layout` 必须携带完整 `navigation` 与 `header` 默认对象（本次按客户端 `LayoutSettings`/`NavigationSettings`/`HeaderSettings` 的默认值补全）。
- **建议**：把两处改成可选链（`layout.navigation?.items`），并加一条测试：`layout` 只有 `{start}` 时 `/api/project` 仍应 200。

### P0-3 定时客户端脚本只在 `/home` 启动 → 同一工程在不同入口行为不一致

- **位置**：`client/src/app/home/home.component.ts:185-197` `initScheduledScripts()`；`client/src/app/view/view.component.ts` **无等价逻辑**。
- **机制**：只有 `mode===CLIENT && scheduling.interval>0` 的脚本会被 `setInterval` 执行，而这段代码**只挂在 home 组件**上。
- **实测**：同一工程、同一画面，`/home` 下标题栏时钟走秒（18:29:12 → 18:29:16，与墙钟一致），`/view?name=AI检测` 下时钟停在静态值 `07:12:36` 不动。
- **后果**：大屏/演示通常用 `/view`（`app.component.ts:180` 对 `/view` 隐藏开发导航，说明它是正式的展示路由），于是"现场看是活的、大屏看是死的"。
- **修复建议**：把 `initScheduledScripts` 抽成公共能力（服务或基类），两个入口都调用；并补一条"同一工程在两个入口下脚本都会跑"的用例。

## §3 架构健康度

### 3.1 分层是清晰的，而且被测试固化

| 层 | 现状 | 证据 |

### 3.4 一致的设计模式：注册表 + 加载表

平台大量使用"**声明式注册**"：控件注册表（`gauges.component.ts:81` 的 `static Gauges`）、形状加载表（`shapes/shapes.js:11`）、存储后端注册（`storage/registry.js`）、设备类型派发（`runtime/devices/device.js`）、后端 API 域汇总（`api/index.js`）、SPA 路由表（`SHELL_ROUTES`）。

- **优点**：扩展点明确、有统一外壳（新增驱动不用动运行时其它部分）。
- **系统性代价**：**"漏注册/漏同步"成了本项目最主要的错误模式**——功能"看起来写好了但不生效"（形状文件存在但没进加载表）、"保存静默失败"（命令表单边改动）、"刷新白屏"（路由表漏一条）。这三类问题在 §2 与 §5 里反复出现，根子都是**多张手工表之间没有守卫**。

### 3.5 健康度评分（主观但可核对）

| 维度 | 评分 | 依据 |
|---|---|---|
| 分层与依赖方向 | **好** | 有正/反向依赖测试 |
| 测试的"结构性"收益 | **好** | 架构测试、授权套件、存储契约套件都是真东西 |
| 扩展点清晰度 | **好** | 8 类扩展任务都能写成"改哪几个文件"（见程序编制手册 §5） |
| 配置驱动的健壮性 | **差** | 工程数据缺字段/缺表 → 直接 4xx + 空画布，且前端不可读（P0-2） |
| 跨层表一致性 | **差** | 路由表、命令表、设备类型、形状加载表全是手工双份（P0-1、P2） |
| 运行入口一致性 | **差** | `/home` 与 `/view` 能力不对等（P0-3） |
| 文档与代码一致 | **差** | 版本/路径/上游三处漂移（§4.1） |

> 一句话：**工程化程度高于"屎山"的平均水平，但"配置与注册表的一致性"是它唯一的、也是反复发作的软肋。**

### 4.6 新增：P1 与 P2（本次核查新发现的隐患，未复现为线上故障）

#### P1 权限过滤用"字符串坐标"往 SVG 源码里插属性

- **位置**：`server/runtime/project/index.js:1202-1223`（逐 item 的权限过滤）。
- **机制**：对无权限的控件，**不改数据模型**，而是：
  1. `var position = view.svgcontent.indexOf(item.id);` —— 在 **SVG 源字符串**里找该 id 第一次出现的位置；
  2. `position += item.id.length + 1;` —— 假定 id 后面**正好紧跟一个字符**；
  3. 把 `' visibility="hidden" '` 用 `slice()` 拼进字符串。
- **风险**：
  - `indexOf` 只找**第一次**出现。若该 id 文本先出现在别处（`<title>`、注释、或另一个元素引用它），插入点就落在**错误的元素/错误的位置**，直接破坏 SVG 结构；
  - `+1` 对"属性顺序不同""id 后面不是单引号/空格"的元素不成立；
  - 这类破坏**不会有异常**，只表现为画面渲染错乱——最难排查的一类。
- **触发条件**：只在"配了权限的非管理员用户"这条路径上触发——**平时不出现，交付现场出现**。
- **等级**：**P1**（触发即画面损坏）。
- **建议**（按优先级）：
  1. 在**模型层**打标记（给 `item` 追加 `hidden` 字段），由前端渲染时处理——一次改到位；
  2. 至少要改成**正则定位完整属性**：`new RegExp('id="' + escapeRegExp(item.id) + '"')`，在匹配到的属性后插入；
  3. 补一条测试：构造"id 同时出现在 `<title>` 与元素上"的 view，断言隐藏的是元素而不是 title。
- **同段的可取之处（客观记录，不是缺陷）**：导航/页眉项按权限是**直接从数组 splice 删除**（`:1184-1200`），服务端返回的已是过滤后的菜单——方向是对的；服务端脚本在非 CLIENT 模式下会**删掉 `code` 字段**再下发（`:1179`），CLIENT 模式保留（`:1176-1178`），因为前端要执行。

#### P2 服务端命令表里有重复键（说明这张表是手抄的）

- **位置**：`server/runtime/project/index.js:1312-1313` —— `SetText: 'set-text'` **连续写了两次**（复制粘贴残留）。
- **影响**：值相同，**当前功能无影响**（JS 对象后者覆盖前者，值一样）。
- **真正的意义**：它证明这张表**没有生成机制、没有校验**——所以才会有重复键活到今天。
- **等级**：**P2**（债务/一致性）。

#### P2 两张命令表必须手工同步（无生成、无校验、无测试）

- 客户端：`client/src/app/_models/project.ts:54` 的 `enum ProjectDataCmdType`
- 服务端：`server/runtime/project/index.js:1302` 的 `const ProjectDataCmdType = {}`（分派在 `:217-220`）
- **后果**：新增命令漏改任一侧 = **保存静默失败**（用户以为保存成功，其实没落库，且无任何报错）。
- **建议**：二选一——
  1. **加一致性测试**（低成本）：从 `project.ts` 解析枚举键，与服务端对象键双向比对；
  2. **生成**（正解）：以 `_models/project.ts` 为单一事实源，构建时生成服务端表，或服务端改为按字符串直接分发。
